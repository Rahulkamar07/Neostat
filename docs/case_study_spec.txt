AI ENGINEER INTERNSHIP
Technical Case Study
Intelligent Document Extraction, Validation & API Platform
1. Problem Statement
Financial-services teams frequently receive invoices and financial statements in native or scanned PDF / JPG / PNG format. Different layouts, image quality, OCR errors and varying financial line items make manual extraction slow and inconsistent. The organisation wants a reusable Document Intelligence service that can extract the complete information present in a document, validate key financial relationships and make processed results available through a deployed dashboard and REST APIs.
Your task is to design, build and deploy a working prototype that performs the complete flow below:
2. Documents in Scope
Only these four document categories are in scope. Automated document schema-selection logic are NOT required for this case study. The document type may be selected in the frontend and sent as request metadata to the API. The assessment focuses on extraction completeness, accuracy, validation, API design, storage and deployment.
3. Input Requirements
Support PDF / JPG / PNG documents only. UnSupported uploads must be identified and rejected as unsupported.
Support both native PDFs and scanned/image-based formats using text extraction and/or OCR as required.
Support documents up to 3 pages.
Validate file type, empty/corrupted files, page count and basic file integrity before extraction.
Document validation is the input-control layer; it is not document-type classification.
4. Mandatory Functional Requirements
4.1 Document Validation
Before OCR or AI extraction, validate the uploaded file. A valid submission must be a readable PDF / JPG / PNG of no more than 3 pages. Unsupported formats, empty files, corrupted PDFs or documents exceeding the page limit must fail gracefully with a clear error response.
4.2 Complete Field & Table Extraction
Extract ALL meaningful information visible in the document, not only a small fixed list of fields. This includes header fields, dates, parties, currencies, totals, financial statement line items, comparative-period values, and invoice/statement tables where present. Values must accurately reflect the source document. Missing values must be returned as null; the system must not invent or infer a value that is not supported by the document.
4.3 Evidence / Grounding
For extracted values, provide supporting source text where practical. Page number is strongly preferred. Evidence must allow the evaluator to trace important extracted values back to the source document. A confidence score is OPTIONAL. 
4.4 Validation
Important: Financial calculations must be based on the actual fields present in the source document. If a field required for a particular validation is not present, the validation should return NOT_APPLICABLE rather than assume or invent a value.
The validation result must be included in the structured JSON and should contain the formula/check performed, input values used, calculated value, reported value, variance and PASS / FAIL / NOT_APPLICABLE status.
4.5 Processing Status
5. Mandatory REST API
The deployed backend must expose REST APIs. Swagger/OpenAPI documentation must be available on the deployed environment.
5.1 POST Request
The API may process synchronously for this assignment. The processed result must be stored so that it appears in the frontend dashboard and can later be retrieved by document name. If the same document name is processed more than once, the GET-by-name endpoint should return the latest result; retaining prior versions is optional.
5.2 Mandatory Structured Response
The exact internal implementation may differ, but the response must be valid JSON and consistent across requests. It must include document name, supplied document type, file validation, complete extracted data as clear key-value pairs, financial calculation validations, processing status and processing metadata. Confidence scores are optional. If provided, they should be meaningful and explainable rather than arbitrary LLM-generated values.
5.3 Error Response
6. Mandatory Frontend
A deployed frontend must be provided using HTML/CSS (JavaScript may be used where required) and connected to the deployed Python API/application. FastAPI, Flask or another suitable Python web/API framework may be used. A separate React, Node.js or similar frontend stack is not required.
Document type selection, PDF / JPG / PNG upload control and Process action.
Dashboard showing all processed documents with document name, type, status and processed time. Confidence may be displayed if implemented.
Allow the user to open a processed document result from the dashboard and view extracted fields/tables.
Display extracted key-value pairs, tables/line items and financial validation/calculation results in a clear and readable manner.
Clearly highlight missing/unreadable fields and failed financial validations. If confidence is implemented, low-confidence values should also be highlighted.
Provide a way to view the raw structured JSON returned by the backend.
Frontend must call the deployed backend/API. The processed-document dashboard must be connected to a database or persistent data store (for example SQLite, PostgreSQL, MySQL or an equivalent option) so processed results remain available during evaluation.
7. Mandatory Deployment
Candidates may use any reasonable free/free-tier deployment platform available to them. Paid infrastructure is not expected. The final code must be pushed to a PUBLIC GitHub repository and the repository link must be submitted with the deployment URLs.
8. Required Code / Repository Structure
The following separation of concerns must be preserved. Equivalent naming is acceptable. Candidates should not place the complete application, OCR, extraction, API, database, validation, logging and exception-handling logic into a single file.
9. Technical Expectations
Return all extracted fields as consistent, machine-readable key-value pairs using structured outputs (for example Pydantic/JSON Schema or equivalent). Financial tables and invoice line items should use structured arrays/objects.
Separate file validation, OCR/parsing, extraction, financial validation, persistence/database access and API concerns.
Implement proper exception handling for invalid files, OCR failures, model/API failures, timeouts, database failures and unexpected processing errors. The application must fail gracefully without exposing stack traces or secrets to end users.
Implement meaningful logging for request processing, validation failures, OCR/model calls, exceptions and major processing stages. Logs should be sufficient to diagnose failures during evaluation.
Return appropriate HTTP status codes and consistent error responses.
Do not hardcode document outputs, expected answers or validation outcomes.
Extraction accuracy and completeness carry high weight. ALL meaningful visible fields, values, financial line items and table values should be extracted and returned as proper key-value pairs/structured arrays. Values will be checked against the source documents. Do not hallucinate unreadable or missing values.
Participants are encouraged to use free or free-tier document/OCR services where useful, such as OCR.Space, Google Cloud Vision / Document AI, LlamaParse, or equivalent services. Open-source/local options such as Tesseract, PaddleOCR and EasyOCR are also permitted. Provider free-tier limits and availability may vary, so candidates should select an option appropriate for the 3-day assessment.
Any LLM/model available to the participant can be used. Confidence scoring is OPTIONAL. Implementing a sensible, explainable confidence mechanism adds value to the submission, but candidates will not be penalized for omitting it.

--- TABLE ---
Document | Minimum Financial Validation
Invoice | Where line items are available: Quantity × Unit Price ≈ Line Total. Sum of all line totals should reconcile to the reported subtotal/total where applicable. Where tax is separately shown: Taxable Amount + Tax ≈ Total. Where cash and change are available: Cash Paid - Total Amount ≈ Change. Candidates must handle cases where GST/tax is already included in the displayed total.
Balance Sheet | Total Capital & Liabilities ≈ Total Assets. Where sufficient line items are available, the sum of individual Capital & Liability components should reconcile to the reported Capital & Liabilities total, and the sum of individual Asset components should reconcile to the reported Assets total. Perform the validation independently for each year/period present in the document.
Profit & Loss | Validate: Interest Earned + Other Income ≈ Total Income; Interest Expended + Operating Expenses + Provisions & Contingencies ≈ Total Expenditure; Total Income - Total Expenditure ≈ Consolidated Net Profit before Minority Interest; Profit before Minority Interest - Minority Interest ≈ Consolidated Net Profit attributable to the Group. Where appropriations are present: Current Profit + Brought Forward Profit ≈ Total Available for Appropriation. Perform validations for each comparative year/period present.
Cash Flow Statement | Validate: Net Cash Flow from Operating Activities + Net Cash Flow from Investing Activities + Net Cash Flow from Financing Activities + FX / Translation Adjustment ≈ Net Increase in Cash & Cash Equivalents. Then validate: Opening Cash & Cash Equivalents + Net Increase in Cash + Cash Acquired on Amalgamation/Other Applicable Adjustments ≈ Closing Cash & Cash Equivalents. Parentheses/bracketed values must be treated as negative values. Validate each period independently where comparative data is available.
